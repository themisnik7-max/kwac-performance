# KWAC Architecture Reference

Dense reference for fast context-loading — read this before exploring the codebase manually. Update it whenever a change alters something below (new table, new AI surface, a schema-drift fix, etc.) rather than leaving it stale.

## Stack

Next.js 14 App Router + TypeScript, Supabase (Postgres + Auth + Storage), Tailwind, deployed on Vercel. No ORM — `@supabase/supabase-js` directly. Two client patterns per route:
- **Browser client** (`lib/supabase.ts`, anon key): RLS-enforced, used in client components. Trust RLS, not app logic, for isolation.
- **Service-role client** (most `app/api/**/route.ts`): bypasses RLS entirely. Every such route MUST derive `agency_id`/role from `getAuthedAgent(req)` (`lib/auth.ts`) — never trust a client-supplied `agency_id`/`agent_id`.

## ⚠️ Live schema drifts from migration files — verify before trusting

Migration files in `supabase/migrations/` are the source of truth for *new* changes, but the live DB has repeatedly disagreed with what old migration files claim (manual Supabase SQL-editor edits that never got backported into a migration). Confirmed instances this project has hit:
- `properties.price` doesn't exist (`price_asking`/`price_final` do) — broke the pricing engine, intelligence dashboard, backtest, and `top_producers_by_area` RPC simultaneously until fixed (migrations 023-024, `lib/intelligenceData.ts`, `lib/valuation.ts`).
- `meeting_valuations` was missing `blended_recommended`/`blended_confidence`/`feedback_count`/`last_feedback_sync` (migration 006 never landed) — every valuation save failed silently for a long time because the upsert's error wasn't checked (fixed migration 027).
- `contacts` has **two overlapping name schemes**: `first_name`+`last_name` (original data) and `full_name` (added later). Always go through `lib/contacts.ts`'s `contactName()`/`splitName()`, never assume one or the other is populated.
- `pipeline_properties.wp_id` had no unique constraint despite code assuming upsert-by-wp_id worked; `contacts.phone2` didn't exist despite being queried.
- `PropertyPhotoUpload` (`components/PropertyPhotoUpload.tsx`) uploaded and stored photos correctly, but never fetched existing ones on mount — only right after a fresh upload in that same session. Reopening a property looked like photos "don't save" when they were sitting in storage the whole time (fixed with a mount-time GET). Also had drop-zone styling with no `onDrop`/`onDragOver` handlers at all — drag-and-drop silently did nothing, only click-to-pick worked.
- `open_houses`' real columns were `property_address`/`time_start`/`time_end`, but every call site (`lib/aiAdmin.ts` executeCreateOpenHouse, `app/api/open-house-quick`, `app/board/page.tsx`) assumed `address`/`start_time`/`end_time` — AI Admin's `create_open_house` tool and the quick-create route were silently failing (NOT NULL violation on the real column), and the board page rendered blank addresses/times. Renamed the DB columns to match the code (migration 035) rather than touching every call site.
- `announcements` had no `agency_id` column at all (a real multi-tenancy gap) and its real text column was `body`, not `content` — `app/api/monitor-remind`'s weekly reminder insert was failing, and `app/board/page.tsx` rendered blank announcement bodies. Added `agency_id`, renamed `body`→`content` (migration 035).
- `app/globals.css`'s unconditional `body{}` rule defaulted to **dark** colors (`background:#0d0d0d;color:#e8e8e8`) even though `body.dark`/`body.light` toggle classes exist — except nothing in the codebase ever applies either class (verified: no component sets `body.className`). Since `color` is inherited, any element that didn't explicitly set its own `color` picked up light-gray-on-dark by default — invisible, not just low-contrast, on the light-card backgrounds every page actually uses. Fixed by making light the unconditional default (plus `color-scheme: light` so native form controls don't get dark-themed by the OS/browser either). **This flip regressed a second cluster of pages** (`/dashboard`, `/submit`, `/export`, `/import`) that are a deliberately separate dark-themed "gamification" section (XP/streak, `#111`/`#151515` panels, light text) with no `Shell` wrapper and no explicit background of their own — they'd been silently relying on the old dark body default the whole time. Fixed by giving each an explicit `background:'#0d0d0d'` on its own outer wrapper, matching the pattern `/personal-admin` and `/locked` already used correctly. **Lesson: never rely on an inherited body background/color — always set both explicitly on a page's own root element**, regardless of which way the global default points.
- `weekly_submissions`' real, actively-written field set (`app/submit/page.jsx` + `app/api/submit/route.js`, kept in sync manually — see comments in both) does **not** include `week_start`, `follow_up_calls`, `first_appointments`, `second_appointments`, `listings_taken`, or `contracts_signed`. `app/api/gps/route.ts`'s "realRates" conversion-rate computation and `app/export/page.jsx`'s CSV export both referenced those non-existent names — `realRates` was silently always `null`, and the weekly_submissions CSV export errored on every attempt. Fixed to use the real field names (`cold_calls`, `meet1_seller_live/phone` etc., `meet2_seller`, `excl_listing_sale`+`simple_listing_sale`+rental variants, `contract_seller`+`contract_buyer`) and `submitted_at` (the closest real timestamp) instead of `week_start`.
- `demand_profiles.agent_id` had a foreign key to Supabase's internal **`auth.users(id)`**, not `agents(id)` — inconsistent with every other `agent_id` column in this schema. Invisible for the three original demo accounts (Demo CEO/Admin/Agent) only because those three happened to be seeded with `agents.id == auth.users.id`; any agent created the normal way (a fresh `agents.id`, matched to its login by email — see `lib/auth.ts`) got a silent FK violation the moment anything tried to write a `demand_profiles` row for them, e.g. Personal Admin's Ζητήσεις tab. Found via a `pg_constraint` diagnostic (temporary `_diag_fk_full` RPC, same throwaway-function pattern as the RLS diagnostics) while seeding ZadesHome team demo data — fixed by repointing the FK at `agents(id)` (migration 040) — **but that migration only fixed the FK, not the RLS policies on the same table, which still compared against `auth.uid()`** (fixed properly below).
- **2026-07-11 production-readiness audit found the same `auth.uid()`-vs-`agents.id` bug in five more places**, all stemming from `009_voice_profiles.sql`/`20260626120000_voice_profiles.sql` being hand-written against `auth.uid()` instead of reusing `current_agent_id()`/`current_agency_id()` (migration 002's helpers, keyed by email — the pattern every other table correctly uses): `voice_notes.agent_id`, `property_scouted.agent_id`, and `property_photos.uploaded_by`/`property_documents.uploaded_by` were all still FK'd to `auth.users(id)`, and `demand_profiles`'s two RLS policies (both `agent_own_demands` and, critically, `admin_agency_demands` — meaning even a **real CEO/Admin** couldn't see agency-wide demand profiles via RLS) still used `auth.uid()`. Also found via the same pass: `meeting_properties.first_registered_by` had drifted to `auth.users(id)` live despite migration 006's file explicitly saying `references agents(id)` — another instance of live/file drift, not a code bug. `property_photos`/`property_documents` uploads were a **hard 500 on every real (non-demo) agent's upload** (FK violation, not just an RLS gap), since `app/api/property-photos`/`property-docs` correctly write `caller.id` (`agents.id`) — only the schema hadn't caught up. `voice-ingest.ts` had its own, separate bug compounding this: it never called `getAuthedAgent`, resolving identity via a hand-rolled `auth.users` lookup that fell back to **"the first agency ever created in the system"** if the (structurally-broken) `agents.id == auth.uid()` lookup missed — meaning a real agent's voice-scouted property/demand-profile could get silently filed into the wrong agency entirely. Fixed together (repointing an RLS/FK fix without fixing the write path just moves the break): FK repoints + RLS rewrites to `current_agent_id()`/`is_ceo_or_admin()` (migrations `20260711120100`, `20260711120200`), `voice-ingest.ts` rewritten to use `getAuthedAgent` with no fallback (401 on no match). `property_scouted` has no live write path (voice-ingest's `property_scouted` intent actually writes to `meeting_properties`, not the `property_scouted` table — confirmed via full-repo grep) so it was fixed for consistency, not because it was exploitable today. Live-verified post-fix: demo CEO can still read all four tables agency-wide (RLS didn't over-restrict), and `npm run typecheck`/`npm run test` both pass.
- **The `supabase/002_multitenancy_and_rls.sql`...`009_voice_profiles.sql` files referenced throughout this document as "not in the repo" were actually sitting loose in `supabase/` (not `supabase/migrations/`)** — a previous audit pass missed them because it (correctly) scoped its search to `supabase/migrations/*.sql`. `npx supabase migration list --linked` confirms these were applied to the live DB manually (SQL editor) and were **never registered in Supabase's own migration-tracking table** — only `010` onward are tracked. Practical implication: they're idempotent and their *content* is known (read them before assuming anything about `current_agency_id()`/`current_agent_id()`/`is_ceo_or_admin()` or base RLS is unrecoverable), but a fresh environment bootstrapped purely via `supabase db push` on `supabase/migrations/` would **not** recreate them — this is the real gap, not "unknown policies." One truly lost file: `005_registration_monitor.sql`'s header references a `004_meeting_v2.sql` that doesn't exist anywhere in the repo; its effects are already baked into the live schema, just not reconstructable from source. Not yet backfilled into `supabase/migrations/` with tracked version numbers — do that before ever provisioning a second (staging) Supabase project, or these ~7 files have to be run by hand again from scratch.

- `contacts.agent_id` existed in the schema but nothing ever populated or enforced it — `contacts` had exactly one RLS policy (`ALL`, agency-scoped only, no owner check), so any agent could read *and write* any other agent's owner/client contacts, PII included. `voice-ingest.ts`'s auto-created owner contacts never set it either. Found 2026-07-12 chasing a user report of cross-agent contact visibility after Personal Admin went agency-wide (see Auth/permissions patterns below) — backfilled from the linking `meeting_properties.owner_contact_id` where inferable, RLS split into owner/null/admin-scoped read+write (migration `20260712110000`), `voice-ingest.ts` now sets `agent_id` at creation. **That fix was incomplete**: `voice-ingest.ts`'s find-or-create-contact lookup (both the property owner and, later, the demand client) still searched `agency_id`-wide by phone with no `agent_id` scoping — so agent B logging a new property/demand for a phone number agent A already had a private contact for would silently set `owner_contact_id`/`contact_id` to **A's** contact, one B's own RLS then hid from them. Fixed 2026-07-13 alongside the Personal Admin Πελάτες tab (below) by scoping the lookup to `agent_id = caller OR agent_id IS NULL`, matching `contacts_select`'s actual visibility rule exactly (verified live: nested PostgREST `or=(and(...),and(...))` filter, not two independent `.or()` calls — confirmed empirically that a wrong `agent_id` correctly returns empty even with a matching phone).
- **`contacts` had a live `unique_email_contact` constraint (`UNIQUE NULLS NOT DISTINCT (email)`) not referenced anywhere in `supabase/migrations/`** — created directly against the DB outside the tracked workflow at some unknown point (same drift class as the untracked `002`-`009` files above, just a constraint instead of a table). Two bugs in one: `NULLS NOT DISTINCT` meant at most **one contact in the whole system** could ever have a blank email, and it had no `agency_id`/`agent_id` scoping at all (global, not per-tenant). Found 2026-07-13 the moment Personal Admin's new "a client card doesn't need full details yet" flow tried to create a second phone-only contact. Replaced (migration `20260713100002`) with a per-agent partial unique index (`unique(agent_id, email) where email is not null`) — unlimited contacts with no email, one agent can't create two contacts sharing an email, different agents (even same agency) can each independently hold a contact with the same real address.

**When something looks broken despite the code/migration looking correct: query the live table directly (`curl` the Supabase REST API with the service-role key, or `npx supabase db dump --linked --schema public` for the full picture) before assuming the bug is elsewhere.**

## ⚠️ RLS policy drift — the same table can have a rogue permissive policy

Found (migration 031) 13 tables with an old, pre-multi-tenancy-hardening policy like `for all using (auth.role() = 'authenticated')` — or in one case (`open_houses`) no condition at all — coexisting with a proper agency/owner-scoped policy added later. **Postgres OR-combines permissive RLS policies for the same command**, so the rogue wide-open one alone grants full cross-tenant access regardless of how correct the other policy looks. This was invisible from migration files alone (the rogue policies were never captured in any file) and was only caught by **live-testing** an actual unauthorized request, not by code/policy review.

**If you add/change RLS on a table, verify it by actually attempting the denied operation with a real non-privileged account — don't just read the policy SQL and assume it's the only one active.** To list every policy actually on a table (there's no built-in way via PostgREST): temporarily create a `security definer` SQL function wrapping `select * from pg_policy where polrelid = '<table>'::regclass`, call it via RPC, then drop it (see migration 029→030, and again 035→036, for the pattern). `announcements` had exactly this rogue-policy problem too (`"ann_all"`, `using (true)` for all commands, no agency check) — found and fixed (migration 036) while wiring the Open House→announcement flow. **Any table not yet touched this way should be assumed unverified, not assumed safe.**

**The table-level rogue-policy remediation effort (migrations 029–036) never once touched `storage.objects`** — the exact same "wide open, only caught by direct testing" pattern existed there too, undiscovered until the 2026-07-11 audit: `property-docs` (private bucket — title deeds, contracts, assignment forms) had `auth.role() = 'authenticated'` with **no agency check at all** on SELECT and DELETE, meaning any authenticated agent from any agency could read or delete any other agency's documents directly via the Storage SDK, completely bypassing `app/api/property-docs`'s own correct `agency_id` check (that check only covers callers going through the API route — direct Storage API access was never gated). `property-images`' upload policy had the same gap (lower severity — public-read bucket by design, but still let any agency upload/deface another's listing folder). Fixed (migration `20260711120000`) by adding `(storage.foldername(name))[1] = current_agency_id()::text` to both buckets' policies, matching `gpi-documents`' correct pattern from day one (migration 044) — uploads already wrote to `${agency_id}/...` paths, so this just made RLS check the folder it already had. Live-verified: signed in as demo CEO, listing objects under the account's own `agency_id` prefix succeeds; listing under a different (fake) `agency_id` prefix now returns empty instead of real objects. **`gpi-documents` remains the only bucket that got this right from the start — treat every other current or future bucket as unverified until it's explicitly checked.**

## Data model — which "properties" table is which

- **`agencies`** — tenant. **`agents`** — staff (`role`: `agent`/`admin`/`ceo`; `admin`/`ceo` treated the same everywhere via `isCeoOrAdmin()`).
- **`contacts`** — people: sellers/landlords OR buyers/tenants. An "owner" is just a contact referenced by `meeting_properties.owner_contact_id` — not a separate table/role. A contact does **not** require a property or demand to exist (Personal Admin's Πελάτες tab, added 2026-07-13, is the agent's full client book — see below); `google_resource_name` (nullable, unique per `agent_id`) is set when a row came from the Google Contacts sync rather than manual entry or a property/demand auto-create.
- **`meeting_properties`** — the agency's own live property pipeline, one row per property the agency is handling. Status flow: `pending` (private to the owning agent) → `for_appraisal` (promoted to shared "Meeting Ακινήτων" review) → `estimated` → `completed`. This is what Personal Admin and Meeting Ακινήτων both read, filtered differently (Personal Admin: `agent_id = you`; Meeting Ακινήτων: your own regardless of status, or anyone's once past `pending` — enforced by RLS, see migration 021).
- **`properties`** — comp/reference data: iList-imported listings (`price_asking`, sometimes `price_final`/`days_on_market`/`sold_at` once closed). Agency-scoped comps only — registry rows live in `market_transactions`, not here. Has `lat`/`lng` (populated on a handful of rows) and, as of migration 033, `balcony`/`utilization_score` (added for the NN pricing model, not yet backfilled on historical rows).
- **`market_transactions`** — real government transfer-registry data (Ministry of Finance "Μητρώο Αξιών Μεταβιβάσεων Ακινήτων", `lib/mamaRegistry.ts` + `app/api/market-data/import-registry`). **No `agency_id`** — deliberate exception to the multi-tenant rule, since this is national public reference data every tenant should see the same copy of. Supplements `properties` as a comp pool in the pricing engine; area-mapped via a curated dictionary (government uses formal municipality/district names, this app uses informal neighborhood names — unmapped rows are kept with `area: null`, not guessed).
- **`pipeline_properties`/`pipeline_events`** — separate, WordPress-sourced sync feed (zadeshome.com), unrelated to `meeting_properties`.
- **`meeting_valuations`** — one row per `meeting_properties.id`, the pricing engine's output (see below).
- **`meeting_comments`** — feedback on a valuation; write-only via `/api/meeting-comments` (direct client insert is RLS-denied on purpose), restricted to the property's area's top producers or admin.
- **`demand_profiles`** — buyer-side leads. Linked to `contacts` via `contact_id` (added 2026-07-13, migration `20260713100000`) — set by `voice-ingest.ts`'s same find-or-create-by-phone logic `meeting_properties.owner_contact_id` already used, backfilled once for existing rows by same-agent phone/email match. `app/contacts/[id]/page.tsx`'s "Ζητήσεις" section now queries this FK directly instead of a fuzzy `client_phone`/`client_email` OR-match.
- **`marketing_campaigns`/`marketing_campaign_recipients`** — email/SMS campaign sends + click tracking (`/api/marketing/track`).
- **`ai_admin_usage_daily`/`ai_admin_actions_log`** — AI Admin chat's daily cap + full audit trail (every turn logged regardless of outcome).
- **`valuation_calibration_log`/`valuation_backtest_results`** — pricing engine audit trail (every blend logged; holdout backtest results).
- **`pricing_model_runs`** — one row per NN training run (weights as JSON, holdout accuracy, sample sizes); most recent `is_active=true` row per `agency_id` is what `meeting-valuation` loads. Old runs kept (not deleted) so accuracy trend over retrains is visible.
- **`open_houses`** — scheduled event (address/date/times/agent/agency), created either via `/api/open-house-quick` (Dashboard, looks up a `properties` row), `lib/aiAdmin.ts`'s `create_open_house` tool, or `/api/marketing/open-house-announce` (MarketingKitPanel's brochure action — also creates the linked announcement below). `/api/open-house-volunteers` enforces a 2-agent signup cap per open house.
- **`announcements`** — general board posts (`app/board/page.tsx`, "Ανακοινώσεις" tab), plus system posts like the compliance reminder (`/api/monitor-remind` — despite the "weekly" framing this implies, it is **not** on any schedule; it's a manual button on Monitor's admin page, `sendReminder()` in `app/monitor/page.tsx`, and only posts when an admin/CEO clicks it). `open_house_id` (nullable FK) links an announcement to an `open_houses` row — when set, the board renders a click-to-volunteer widget backed by `open_house_volunteers` directly on that announcement card.
- **`agents.team`** — plain text, nullable; `null`/empty = solo agent, a string = that team's name. No separate `teams` table (not needed yet — no team-level settings exist beyond the name). Live column, never captured in a migration file (same drift pattern as everything else in this section). Currently: **ZadesHome** = Xenofon Zades, Themis Nikolaou, Alexandra Georgaki, Tzikas; everyone else (Katerina Karpouzopoulou, Demo Agent) is solo; Demo CEO/Demo Admin have `team: null` (oversight roles, not team members). All 4 ZadesHome agents plus Katerina now have real Supabase Auth logins (their `@kwgreece.gr` email / `KwacDemo2026!`) — three of them (Xenofon/Themis/Alexandra) previously existed only as `agents` rows with no matching auth user at all and could never have logged in.
- **`weekly_submissions`** — the one actively-used activity-tracking table (`/submit`, weekly self-reported counters: calls, meetings, mandates, contracts, offers, deposits — see `SECTIONS` in `app/submit/page.jsx` for the full, current field list). Everything else described as "GPS"/production data (`showings`, `offers`, `property_closing`, `property_mandate`, `sold_properties`, `sprint_entries`, `badges` tables) exists as real, well-formed schema but has **zero write path anywhere in the app** — they're empty and will read as empty until a UI is built for them. Don't assume a table having a sensible name and columns means it's live.

## Three distinct AI surfaces — do not conflate them

1. **Voice extraction** (`lib/voice/*`) — OpenAI Whisper (speech-to-text) + GPT-4o-mini (structured JSON extraction, `temperature: 0`). Used for property/demand voice notes (`/api/voice-transcribe`, `/api/voice-ingest`). Regex-based extraction is preferred over the LLM wherever possible (phone/email/price/size) — the LLM only fills fields regex can't get, to keep token spend down.
2. **AI Admin chat** (`lib/aiAdmin.ts`, `components/AiAdminChat.tsx`, `app/api/intelligence-chat`) — Anthropic Claude (Haiku 4.5, cost/speed over Sonnet since this is mostly short structured extraction + grounded Q&A), tool-calling. Floating widget, global on every page via `AppShell`. Low-risk actions (`add_contact`, `create_open_house`) execute immediately; anything sending to an external party (`send_email`) always previews and requires a separate confirm call that does **not** re-invoke Claude (token efficiency — the confirm step just executes the already-shown action). Daily per-agent cap (`DAILY_ACTION_CAP` in `lib/aiAdmin.ts`), checked *before* calling Claude so a request over the cap costs zero tokens. **Added 2026-07-11**: a per-minute cap (`lib/rateLimit.ts`'s `checkRateLimit`, backed by the generic `check_rate_limit` RPC, migration `20260711130000`) sits in front of the daily one — the daily cap alone didn't stop a scripted/compromised session from burning a whole day's allowance in seconds. Same primitive now also caps `/api/voice-transcribe` + `/api/ai-admin/transcribe` (5/min/agent — real OpenAI $ per call, previously uncapped) and `/api/register` (5/hour/IP — previously unlimited signup attempts and email-existence enumeration via its 409 response). `check_rate_limit` is a reusable fixed-window counter (any route can call it with its own key/window/limit); it fails open on its own infra errors so a rate-limit bug can never be the reason a legitimate request gets blocked. **Also added 2026-07-11**: `callClaude` (`lib/aiAdmin.ts`) now (a) sends the system prompt as two blocks — a static instructions/rules half with `cache_control: {type:'ephemeral'}`, and a dynamic date+portfolio half without — plus a `cache_control` marker on the last `TOOLS` entry, so the ~13 tool schemas and the rules text are Anthropic-cached instead of re-sent in full every single call (up to 90% cheaper on the cached portion once it clears Haiku's minimum cacheable block size — harmless, silently ignored, if a block doesn't clear it); (b) retries a 429/5xx from Anthropic up to twice with short jittered backoff — this was the one Claude call site in the app with zero retry of any kind, a real gap once concurrent usage is high enough to hit Anthropic's account-level rate limit before any per-agent cap does; (c) the static instructions now include one explicit line telling Claude to treat portfolio/tool-result content as data, not instructions — defense-in-depth against indirect prompt injection for if/when the planned pgvector/RAG layer starts feeding retrieved free-text (comments, contact notes) into this same system prompt. **Note on tool-calling threat model**: the `TOOLS` array is a fixed, enumerated set of ~13 narrow business actions — there is no generic "query table X" or "run SQL" tool exposed, and every executor re-derives `agency_id`/`agent_id` from the authenticated caller server-side rather than trusting anything Claude generates as an identity/scope claim. A successfully-injected instruction cannot escalate past what the real logged-in caller could already do through this surface — keep it that way if new tools are ever added (no tool should accept a caller-identity-shaped parameter from Claude's own output).
3. **Pricing engine** (`app/api/meeting-valuation`) — a three-signal blend, all three logged per-run in `valuation_calibration_log`. **By explicit product decision, only two data sources are allowed to influence the price at all: the government registry, and top-producer feedback.** The agency's own `properties` listings (mostly still-active asking prices, not proven sales) and non-top-producer comments/estimates are excluded from both the live blend and NN training — see `top_producers_by_area`-filtering in both routes below.
   - **Comp-based** (`lib/valuation.ts`) — deterministic, not ML. Comp-weighted average over `market_transactions` only (time-decayed, IQR outlier-filtered) × floor/condition/age multipliers. No black box; every multiplier is a named, inspectable function.
   - **Small neural net** (`lib/miniNet.ts` + `lib/pricingFeatures.ts`) — a from-scratch, dependency-free MLP (2 hidden layers, ~35 input features: sqm, floor, age, renovated, condition, balcony, utilization_score, distance to metro/sea/Acropolis, competing active listings, one-hot neighborhood). Not an LLM, not a framework black box — every weight is plain JSON, forward/backprop is ~150 lines in one file. Trained via admin-triggered `app/api/pricing-model/train` (matches `valuation-backtest`'s "deliberate action, not background job" pattern) on `market_transactions` plus **top-producer-only** `meeting_comments.agent_estimate` rows, folded in as lower-weighted (0.3x) soft training examples — the literal mechanism for "reinforced by agent feedback," not RLHF (no policy/reward model, just supervised learning with weighted samples). Holdout accuracy (`pricing_model_runs.holdout_r2`/`holdout_mae_pct`) is logged every run and directly controls how much the blend trusts it (weight = `0.05 + max(0,r2)*0.35`, capped 0.30). **Fixed 2026-07-10 (migration 043)**: `top_producers_by_area` previously matched an agent via `properties.agent_email`, which has no write path anywhere (the ilist importer only ever populates `agent_name`) — it always returned empty, so `feedback_folded_in` was 0 on every retrain and the "reinforced by feedback" mechanism was fully dormant. Now matches on normalized `agent_name` (trimmed/lowercased) scoped to `agency_id` instead. **Still a text match, not a stable FK** — Greek name variants (accents, name-order, nicknames) can still miss. The durable fix is a real `agent_id` FK captured on `properties` at import time; that needs a product decision on what happens on an ambiguous/no match, so it wasn't done silently here. Latest run (2026-07): 811 train / 143 holdout rows, all registry: R²≈0.17-0.32 (varies by seed), median error≈34-36% — real signal, not sophisticated yet. **Fixed 2026-07-11**: `app/api/pricing-model/train` used to deactivate the previous active run *before* inserting the new one — a timeout or crash between those two statements left the agency with **zero** active `pricing_model_runs`, silently dropping the NN signal from every valuation until the next successful retrain. Now inserts the new run first (as active), then deactivates everything else; a mid-write failure now briefly leaves two "active" rows instead of zero, which is harmless since `runValuation()` already takes only the single most recent one. Also claims `maxDuration = 60` (Hobby ceiling) now, matching `import-registry`'s pattern — training over a growing `market_transactions` table had no explicit duration budget before.
   - **Top-producer feedback** — `meeting_comments.agent_estimate`, filtered to that area's top producers only (same known-empty-today caveat as above).

   **Meeting Ακινήτων is open engagement for everyone, training-eligible for few**: any agent can vote agree/disagree and comment on a valuation once it exists (`/api/meeting-comments`, no longer gated) — displayed as history (`% agree`, comment feed) in the Meeting Ακινήτων UI — but only top-producer-authored feedback is filtered back in server-side to actually move the price or the NN's weights.

   The full computation lives in `lib/pricingEngine.ts`'s `runValuation()`, callable from two places: `app/api/meeting-valuation` (admin/CEO-gated manual re-run) and `app/api/meeting-properties/set-status` (no gate — fires automatically, system-triggered, the moment *any* agent moves their own property to `for_appraisal`, so the estimate already exists by the time anyone opens it; `app/meeting/page.tsx`'s admin-open effect is a fallback for the rare case a property reaches `for_appraisal` some other way, e.g. a future bulk-import path). Report text is a handful of short emoji-prefixed lines (`\n`-joined, rendered as a bulleted list), not a dense paragraph — capped by construction at ~5 lines (comp basis, top comp, NN factors, sale probability, feedback count), each conditional on the data actually existing. Admin finalizes review with "Ολοκλήρωση Εκτίμησης" (marks `completed`, jumps to the next queued property).

   **Fixed 2026-07-11 (migration `20260711120600`)**: the two call sites above can race each other for the same property (auto-trigger + a manual re-run, or a double-submit) — `runValuation()`'s write phase used to be 4 independent statements with no lock, so overlapping calls interleaved: last `meeting_valuations` upsert silently won, and both inserted their own `valuation_calibration_log` row, permanently duplicating the audit trail. Now a single `security definer`-free RPC, `write_valuation_result(property_id, valuation jsonb, calibration jsonb)`, wraps all 4 writes in one transaction and takes a `pg_advisory_xact_lock(hashtext(property_id))` first — concurrent calls for the *same* property serialize instead of interleaving (different properties never block each other); the lock auto-releases when the RPC's implicit transaction commits. As a side effect the calibration-log insert is no longer allowed to silently fail independently of the valuation write (previously tolerated as non-fatal) — they now succeed or fail together.

   Also computes an honest probability-of-sale-within-6-months (empirical frequency table over closed comps, reports "insufficient data" below 8 comps rather than a fabricated percentage) and cites the top comparable by address/size/days-on-market in its reasoning text — never a fabricated name.

## AI data as company "soul" — retention + future fine-tuning/RAG direction

Explicit product direction (2026-07): `ai_admin_actions_log`, `valuation_calibration_log`, `meeting_comments`, `ai_admin_usage_daily`, and anything else that logs an AI decision or an agent's response to one, are being kept as durable training data — eventually either (a) fine-tuning an **open-source** model (e.g. Llama 3) on the company's own accumulated history, or (b) a `pgvector`-backed retrieval layer so Claude (the AI Admin) can pull up "what actually worked here before" as context, not from its own training data.

**Standing rules this implies, going forward:**
- **Never add a cleanup/TTL/archival job that deletes rows from these tables.** Nothing in the codebase does today (verified) — keep it that way. If a table genuinely needs pruning for cost/performance reasons later, archive (move to cold storage), don't delete.
- **New AI-adjacent features should log real inputs/outputs, not just a summary.** `ai_admin_actions_log.tool_args`/`result_summary` already do this reasonably; keep that bar for anything new.
- **Outcome/conversion signal is the actual bottleneck, not row count.** `marketing_campaign_recipients` (click tracking) and `valuation_calibration_log` + `valuation_backtest_results` (predicted vs. actual, holdout accuracy) are the two places that already close the loop — action → real-world result, not just action → logged. Most AI Admin actions (`add_contact`, `create_open_house`, etc.) don't have any downstream outcome link yet, and closing that gap generically (without inventing a fake "success" for actions that don't have one) is unsolved — worth a dedicated design pass before investing further in fine-tuning/RAG on top of it.
- **`ai_insights`** table (`insight_type, content, data_snapshot, thumbs_up, thumbs_down`) already has exactly the schema for capturing human-rated AI output, but nothing in the app reads or writes it — fully dormant. Wiring this up (even just a thumbs up/down on AI Admin replies) would be a cheap, high-value next step toward real "what worked" data.
- **`pgvector` extension is enabled** (migration 041) but **no embeddings table exists yet, on purpose** — every candidate source table's real (non-demo) row count is single-to-low-double-digits today; a similarity search against that little data has nothing useful to retrieve. Build the embeddings table + generation pipeline once real usage volume exists, not before.
- **Fine-tuning target, if/when pursued, should be the AI Admin assistant (tone, domain knowledge, tool-selection judgment) — not the pricing engine.** The property valuation model is deliberately staying a small, transparent, from-scratch network (`lib/miniNet.ts`) per the explicit no-black-box decision already made for that specific system — that decision is unrelated to and unaffected by this AI-Admin-focused direction, and the two shouldn't get conflated later.

## Self-registration + admin approval

`app/api/register/route.ts` is the only public (no session) write route in the app. It gates self-registration to the agency's `allowed_email_domain` (case-insensitive), then checks `agencies.require_approval`: if true, the new `agents` row is created with `is_active: false` instead of `true`, and the response tells the user their account is pending. **This is real enforcement, not a UI flag** — `getAuthedAgent` (`lib/auth.ts`) rejects any agent with `is_active === false` on every service-role route, the same fail-closed check already used for a deactivated `agencies.system_active`. A pending agent can still complete Supabase Auth sign-in (the auth user is created/confirmed at registration time either way) and the browser-side RLS-backed agent lookup in `AppContext` still succeeds (RLS isn't gated on `is_active`) — so `components/Shell.tsx` explicitly checks `agent.is_active === false` and renders a "pending approval" message instead of the page, purely for UX; the actual security boundary is `getAuthedAgent`, not this client check.

CEO/Admin approve or reject via `app/api/agents/pending` (`GET` lists `is_active=false` agents in the caller's own agency; `POST {agent_id, action}` with `action: 'approve'` flips `is_active` true, `action: 'reject'` deletes both the `agents` row and the Supabase Auth user, freeing the email for re-registration) — surfaced as a "🔓 Εγκρίσεις" tab on `/monitor`. Both actions re-verify `target.agency_id === caller.agency_id` server-side before acting, same pattern as `canActAs` — a service-role client has no RLS backstop. Live-verified end-to-end 2026-07-11: registered a synthetic pending agent, confirmed `is_active:false` and a real protected route (`/api/gpi/clients`) 401'd for it, approved via the endpoint, confirmed the *same* bearer token then got 200 with no re-login — and separately verified the reject path deletes cleanly and frees the email. No migration needed — both `agencies.require_approval` and `agents.is_active` already existed live; this was purely an unenforced application-logic gap.

## Sprint Calls — folded into Μετρησιμότητα, surfaced on Dashboard

`app/sprint/page.tsx`'s live-session call counters (`calls`/`leads`/`appointments` on `sprint_entries`) used to be a fully separate counter system with no connection to `weekly_submissions`. `app/api/sprint/entry/route.ts` now does both in one call: upserts `sprint_entries` (for the live leaderboard) **and** folds the delta into the agent's current-week `weekly_submissions` row via a fixed mapping — `calls`→`cold_calls`, `leads`→`leads_cold`, `appointments`→`meet1_seller_phone` (a sprint is cold-calling, so its "appointment" is specifically a phone-set 1st appointment) — with matching XP weights, so sprint activity earns the same XP a manual `/submit` entry would. `lib/weekInfo.ts`'s `getWeekInfo()` (extracted from `app/submit/page.jsx`, which used to have its own inline copy) is what decides which week a sprint call lands in. **Fixed 2026-07-11 (migration `20260711120500`)**: this fold used to be a JS read-modify-write (read both rows, compute a delta in Node, upsert the whole row) — a double-tap or two devices on one account raced and silently lost an update, with no error. Now a single row-locked RPC, `upsert_sprint_entry_and_fold` (`SELECT ... FOR UPDATE` on the `sprint_entries` row, then both writes in the same transaction), called from the route instead of the old two-step JS logic.

## Auth/permissions patterns

- `getAuthedAgent(req)` — resolves the caller's agent row from their bearer token. Every service-role route needs this. **Also checks the caller's agency is active as of 2026-07-11** (`isAgencyActive`, 5-min cache) — previously the `system_active` kill-switch (`middleware.ts`) only covered page navigation (its matcher excludes `api/`), so a locked-out agency's API access kept working fully even while their UI redirected to `/locked`. Fixing this also caught a second bug in the same area: `middleware.ts`'s own check was `agencies.select('system_active').limit(1)` — **global, not scoped to the visitor's own agency** — the third instance this session of the "first row/agency in the system" single-tenant shortcut (see `voice-ingest`/`ingest-cron`/`pipeline-sync` above). `getAuthedAgent`'s version is properly scoped to `agent.agency_id`; `middleware.ts`'s own check is left as-is (still global) since it's UX-only now — the real enforcement boundary moved to `getAuthedAgent`, which covers every service-role route without per-route wiring. **If you're grepping for this bug class in future work: `.limit(1)` with no `.eq(..., callersOwnId)` anywhere near an `agencies`/tenant-identifying table is the tell.**
- `isCeoOrAdmin(agent)` — role check.
- `canActAs(agent, target_agent_id)` — "can `agent` act on behalf of `target_agent_id`"; true for self, or admin/CEO **only within the same agency** (looks up the target's `agency_id` — don't skip this check, an early version trusted role alone and let a CEO in one agency act as any agent anywhere).
- Admin-gated actions in this codebase: manually (re-)triggering an AI valuation via `/api/meeting-valuation` (the *automatic* trigger on entering `for_appraisal` is deliberately not gated — see pricing engine section above). Meeting Ακινήτων comments are open to any agent once a valuation exists; only which comments count toward the price/model is gated (top-producers-of-the-area only), not who can write one.
- **RLS hides rows, not columns — redact PII server-side when a row is intentionally agency-wide readable.** `meeting_properties`/`demand_profiles` are correctly agency-wide readable (agents need to see what colleagues are working on), but that means `owner_name`/`owner_phone`/`owner_email`/`seller_motivation` and `client_name`/`client_phone`/`client_email` rode along on every row too — no RLS policy can show a row but null out specific columns. Fixed 2026-07-12 via `lib/properties.ts`'s `redactPropertyIfNotOwner`/`redactDemandIfNotOwner`, used by three new routes (`/api/personal-admin/properties`, `/api/personal-admin/demand`, `/api/properties/[id]`) that fetch server-side with the service role and strip those specific fields for anyone but the uploading agent or admin/ceo, before the JSON ever reaches the browser. Same shape as `redactGpiClient` in `lib/gpi.ts` — **this is the general pattern for "row is visible, some columns on it aren't": redact in a server route, not in RLS.** `meeting_properties_update` itself was already correctly owner-or-admin scoped at the RLS level (verified live via `pg_policies`, not just trusted from the code comment claiming it) — only the read side needed this.
- Shared-secret comparisons (`CRON_SECRET`, `INTERNAL_API_SECRET`) now use `lib/secureCompare.ts`'s constant-time `secureCompare` instead of `===` — closes a timing side-channel, low real risk given secret length but zero-cost to fix. Upload routes (`property-docs`, `property-photos`, `gpi/upload`) sanitize the file extension via `lib/uploads.ts`'s `safeExtension` (whitelist `[a-z0-9]{1,5}`) before building the storage path — the bucket-folder prefix was already server-constructed and not attacker-controlled, so this closes a narrower "extra path segment via a crafted filename" gap, not a cross-tenant one. `next.config.js` sets `X-Frame-Options`/`X-Content-Type-Options`/`Referrer-Policy`/`Permissions-Policy`/`Strict-Transport-Security` — deliberately no CSP yet (would need a page-by-page script/style/img source audit first; the app loads i-list.gr images and a Leaflet map across many pages, and a wrong CSP silently breaks whichever page nobody happens to click through right after deploy). `Permissions-Policy` allows `geolocation=(self)`, not `()` — `app/valuation/page.jsx` uses `navigator.geolocation` for address autofill; caught before shipping by grepping for actual usage first.

## GPI — long-term rental / property-management client tracking

New domain (migration 044), deliberately not linked to the sales/valuation tables above — a landlord's ID, TIN, taxisnet credentials, and the unit(s) they have in the program. Lives in the same Supabase project as everything else (not a separate database), but access is intentionally tighter than the rest of the app:

- **`gpi_clients`** (the owner/landlord) — **`gpi_units`** (a specific property/lease of theirs, `client_id` FK) are separate tables because one owner can have multiple units; keeping them separate avoids duplicating a landlord's TIN/ID/taxisnet fields per unit. `gpi_units.agent_id`/`agency_id` are denormalized from the client at insert time so RLS doesn't need a join.
- **Access is restricted to the assigned agent + admin/ceo only** — not agency-wide like properties/contacts. Same RLS shape as `weekly_submissions`/`sprint_entries`/`gps_goals` (`agent_id = current_agent_id() or is_ceo_or_admin()`).
- **Taxisnet username/password/authentication key are encrypted application-side** (`lib/crypto.ts`, AES-256-GCM, key from `GPI_ENCRYPTION_KEY` env var — not in the repo, must be set in `.env.local` and Vercel) before they reach Postgres. `lib/gpi.ts`'s `redactGpiClient()` strips the ciphertext entirely from every list/detail API response — the browser never receives it, encrypted or not. Plaintext only ever leaves the server via `POST /api/gpi/clients/[id]/reveal`, which re-checks access and logs every call to `gpi_credential_access_log` (who, which client, when — admin/ceo readable, nothing reads it in the UI yet). **Rate-limited as of migration `20260711120300`**: `canAccessGpiClient` correctly lets an admin/ceo caller reveal *any* client in their agency, which meant nothing previously stopped a compromised admin/ceo session from looping the reveal endpoint over every client and exfiltrating every landlord's taxisnet credentials in one burst. `increment_gpi_reveal_usage` (same atomic-counter pattern as `ai_admin_usage_daily`, hourly instead of daily since reveal abuse plays out in seconds-to-minutes) caps this at 10/agent/hour; a call past the cap is still logged (blocked attempts are exactly what's worth seeing) but never decrypts, and the first blocked call in a burst posts a system `announcements` row so admins see it without needing to think to query the log table.
- ID/passport photo goes to the private `gpi-documents` storage bucket, scoped by the object path's first segment (`agency_id`) in `storage.objects` RLS. `gpi_clients.id_passport_photo_path` stores the storage **path**, not a URL — signed URLs (1hr TTL) are generated fresh on every `GET /api/gpi/clients/[id]`, never persisted, so they can't silently expire in the DB.
- All reads/writes go through `app/api/gpi/**` (service-role client + `getAuthedAgent` + `lib/gpi.ts`'s `canAccessGpiClient()`), the same pattern as the rest of the API surface — RLS on `gpi_clients`/`gpi_units` is defense-in-depth, not the primary access path.
- UI: `app/gpi/page.tsx` (list) + `app/gpi/[id]/page.tsx` (client detail, units, credential reveal, photo upload). No AI surface here — plain CRUD, matching PRODUCT_SPEC.md's rule that deterministic data entry doesn't get a skill/LLM call.
- **Exclusive Leasing Agreement autofill** (migration 045): `components/GpiAgreementDocument.tsx` fills KWAC's real brokerage contract template from a unit's data — shared by the agent's authenticated preview (`app/gpi/agreement/[unitId]`, linked from each unit card on the client page) and the public view an emailed landlord opens (`app/gpi/agreement/view/[token]`). The landlord has no login, so `gpi_agreement_shares` (random unguessable token, 30-day expiry) is the access control for that route — deliberately not the `app/marketing/brochure`-style pattern of embedding data in a `?d=` URL param, since this document carries TIN/National ID. Sending is preview-then-confirm (`POST /api/gpi/units/[id]/agreement/send`), same rule as `skills/listing-marketing-kit`; the email itself is a short Brevo transactional message with a link, not the document inline. One `demo=true` client + unit is seeded by the migration (CLAUDE.md's demo-data rule) so the template is checkable without real client data. **Fixed 2026-07-11**: the send route used to insert the `gpi_agreement_shares` row (a live, 30-day-valid unauthenticated-access token to a document carrying TIN/National ID) *before* attempting the Brevo send — a Brevo failure left a valid, undelivered token behind with no cleanup, and a retry created an additional token rather than reusing/replacing it. Now sends first; the share row (and its token) is only persisted once Brevo confirms success. The `!BREVO_API_KEY` manual-sharing fallback (no email configured, agent copies the link themselves) is unchanged — that's a deliberate no-send path, not a failure, so it still persists the token immediately.
- **Print pages and the office chrome**: `AppShell` renders Sidebar/PageTracker/AiAdminChat on every route except `/login` and (as of this feature) any `/gpi/agreement/view/*` path — see `PUBLIC_ROUTE_PREFIXES`. Printing used to bleed that chrome into the output on every print-ready page (brochure/open-house included); fixed globally via `.app-chrome` + a `@media print` rule in `globals.css`, not just for GPI.

Deliberately per-agent, not per-agency — these are each agent's own Google contacts, matching how `contacts.agent_id` already scopes ownership (see schema-drift log above); two agents in the same agency connect separately.

- **Not configured by default** — needs a real Google Cloud OAuth client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` env vars, not in the repo, nobody but the account owner can create these). `lib/googleContacts.ts`'s `googleOAuthConfigured()` gates every route; every route degrades to a clean `501 {error:'not_configured'}` rather than crashing when unset — live-verified (see below) with the env vars absent, the actual state as of this writing.
- **Manual "Sync now" trigger, not a background cron** — deliberately, per CLAUDE.md's standing warning about background jobs and per-tenant/per-agent config (a scheduled version would need real per-agent looping infrastructure, a bigger decision than this feature needed to make).
- **OAuth flow**: `POST /api/google-contacts/connect` (authed, returns the consent URL — can't 302 directly since the browser needs to navigate there itself) → Google → `GET /api/google-contacts/callback` (Google's redirect, no auth header at all — this app keeps sessions in the browser, not an httpOnly cookie the callback could read, see `lib/auth.ts`). Identity crosses that gap via a signed `state` param: `encodeState`/`decodeState` in `lib/googleContacts.ts` AES-GCM-encrypt `{agent_id, ts}` with the same `GPI_ENCRYPTION_KEY`/`lib/crypto.ts` used for GPI taxisnet credentials — decrypt-or-throw doubles as the tamper check, no separate signature needed. 15-minute freshness window.
- **`google_contacts_connections`** (migration `20260713100001`) — one row per agent, `refresh_token_encrypted` (same `lib/crypto.ts` AES-256-GCM pattern as GPI credentials, never plaintext in Postgres). `contacts.google_resource_name` (unique per `agent_id`) makes repeat syncs idempotent updates instead of duplicate inserts.
- **Sync** (`POST /api/google-contacts/sync`): finds the "KWAC" `contactGroup`, fetches its members, `people:batchGet`s details (chunked 50 at a time, the People API's per-call cap), upserts into `contacts` matching first by `google_resource_name`, then by phone within the same agent, else inserts new. Per-person failures are caught and skipped (one bad row doesn't abort the batch); "no KWAC label found yet" is a normal `200` result with `group_found:false`, not an error.
- **UI lives entirely inside Personal Admin's Πελάτες tab** (`GoogleContactsWidget` in `app/personal-admin/page.tsx`), not a separate settings page — there wasn't one to extend (`/profile` is actually a properties map page, misleadingly named), and this is where an agent is already looking when thinking about their client list.
- **Not yet live-tested end-to-end with a real Google account** — that needs a real Google Cloud OAuth client, which only the account owner can create. Everything up to that boundary (schema, encryption, the not-configured/not-connected failure paths, the contact upsert logic's dedup/scoping rules) is live-verified against the real database; the actual OAuth round-trip and People API calls are not.

## ⚠️ This environment's TypeScript install doesn't narrow discriminated unions

Confirmed via isolated repro (not project-specific): `if (result.success) {...} else { result.error }` on a `{success:true;...} | {success:false;error:string}` union fails to narrow — `tsc` reports `error` doesn't exist even inside the `else`/negated branch, on a bare minimal file with no project config involved. Root cause not chased down (TS 5.9.3, otherwise-standard setup). **Workaround: use `'error' in result` (`in`-operator narrowing) instead of checking a boolean discriminant field** — confirmed working. See `lib/pricingEngine.ts`'s `ValuationResult` type and its two call sites for the pattern.
